# Thor E2E 优化方法

优化的采用条件是：在同一任务契约下，通过正确性与模型质量检查，并获得可复核的端到端收益。KDA 提供内核设计知识和实验工具；框架路径、模型集成与最终验收仍需要围绕实际 workload 组织。

## 1. 冻结任务契约

使用 `tools/new_task.py` 建立独立目录，为 baseline、candidate、benchmark 和结果分别留出位置。把目标写成可以测量的条件，例如指定输入范围下的同步推理延迟、吞吐或内存上限，并写明允许的质量变化。

| 契约项 | 需要记录的内容 |
|---|---|
| 程序身份 | 模型和权重版本、框架/backend、baseline 源码与候选哈希 |
| 输入与计算 | batch、shape、layout、dtype、累加精度、量化/缩放边界、mask、迭代次数 |
| 动态范围 | shape、数值、地址和控制流分别是否允许变化 |
| 执行条件 | stream、CUDA Graph、warmup、cache、并发、power mode |
| 验收条件 | 计时边界、数值阈值、模型质量、性能目标及测量协议 |

固定 shape 不等于固定输入。只固定维度时，图像、状态、随机噪声、权重或中间值仍可能变化。静态地址也不允许缓存计算结果来代替读取新数值。只有任务明确固定的内容才可作为特化前提。

框架 baseline 和 candidate 应使用对称的分配、输出、stream、capture 与计时方式。编译、模型加载、预处理、Graph capture 和请求处理是否计入 E2E，必须在实验前确定。

## 2. 建立 baseline 与 A/A

先在 Thor 上运行真实模型，确认基础数值和执行路径。随后用相同 baseline 做相邻或交错的 A/A 测量，检查 warmup、缓存状态、输入变化、内存压力与时间漂移。若 A/A 波动已经接近目标收益，先改善测量条件或增加采样。

记录 GPU 占用、GPU/EMC devfreq、power mode、可用内存与软件版本。Thor 的 CPU/GPU 共享 RAM，不能把系统可用内存与 Torch 显存统计相加。遇到其他计算进程时推迟测量，或把受干扰样本标记为无效并保留原因。

## 3. Profile 定位瓶颈

在已经 warmup 的代表性请求窗口采集 Torch Profiler 或 Nsight Systems。必要时对关键 kernel 用 Nsight Compute（NCU）检查内存访问、执行资源和流水线假设。Profiler 会影响运行时间，速度比较需要另外采集未插桩数据。

使用同一 trace/window 内的分子和分母报告时间贡献。区分 kernel-duration sum、GPU 区间并集、GPU span、CPU launch 与同步 E2E。多 stream 的 kernel 时间相加可能超过总耗时；空闲区间也不一定完全由 CPU 引起。

阶段和层归属应来自源码、配置、NVTX 或可验证的调用边界。kernel 名称、事件数量或规则化间隔只能提供线索。把 Nsight SQLite 转换为 Chrome trace 时，保留原文件和转换元数据；转换不能补出未采集的 Python 调用栈。

## 4. 按瓶颈选择一个改动

| 观测 | 优先考虑 | 验证重点 |
|---|---|---|
| 重复计算、冗余分支或无用中间值 | 精简框架执行路径 | 实际调用语义、数值与输入变化范围 |
| 大量小 kernel、CPU launch 或同步间隙 | 融合、Graph、减少分配与同步 | capture/replay、stream、缓冲区生命周期 |
| 单个 GEMM/Attention 等占据主要时间 | 查询 KDA/KernelWiki，设计候选 | layout、分块、流水线、实际模型 cache context |
| 拷贝、布局转换或缓存管理成本较高 | 数据路径和缓存布局 | 所有权、更新条件、容量、E2E 中的实际成本 |

无需预设“先框架”或“先算子”。以当前瓶颈决定顺序，写下一项可证伪的假设、一个改变的变量、预期影响和回退条件。不要同时更换精度、布局、调度和计时边界，使收益来源无法判断。

KernelWiki 的 SM90/SM100 经验可用于构造假设，具体指令、cluster、launch 约束和 tuning 参数必须在 Thor SM110 上重新验证。独立算子测试用于快速筛选；模型真实缓存与执行上下文仍决定最终效果。

## 5. 验证数值、stream 与 Graph

每次开发迭代保留基础数值检查，使用随机输入覆盖一般路径；随后用真实输入范围、边界分布或高精度参考检查容易被平均误差掩盖的失败。对归约、softmax、量化、溢出和接近阈值的输入，检查任务相关的误差指标。

完整采用前完成以下检查：

1. 验证目标 shape 与适用的尾部、奇数和边界 shape。
2. 修改输入并污染输出，检查是否重新计算且覆盖全部输出。
3. 在非默认 stream 执行，检查是否遵守调用方 stream。
4. Capture 后修改输入再 replay，检查 Graph 读取新值与缓冲区生命周期。
5. 使用实际模型和质量指标验证最终输出，并按改动风险补充 sanitizer。

逐位一致（bitwise identical）、数值容差内一致和模型质量可接受是不同结论。明确采用哪一种契约。算子误差阈值不能替代模型质量，模型输出误差也不能自动证明闭环任务质量。

## 6. 测量未插桩配对 E2E

在同一冻结契约下使用相邻或交错的 baseline/candidate 对，默认至少保留 20 对有效未插桩样本。把原始数据写为 `templates/paired-e2e.schema-example.json` 所示格式，再用 `tools/thor_metrics.py compare` 分析。无效样本也应保留，并写出排除原因。

报告绝对延迟、candidate/baseline 比值与不确定性，关联 A/A 校准和平台状态。用独立测量窗口确认收益；若结果随窗口反转或与噪声不可分，应继续诊断或报告未能确认。不要拼接不同父版本、输入或窗口的结果来声称同轮累计收益。

## 7. 采用或回退

只有数值、stream、Graph、模型质量和任务性能条件全部满足时才采用。记录 parent/candidate 源码和二进制哈希、命令、原始计时、profile、平台状态及结论。保留失败候选的原因，以便下一次实验知道哪个前提需要变化。

采用后更新 baseline。若主要开销发生变化，重新 profile 再选择下一项改动；如果没有稳定 E2E 收益则回退，避免仅凭独立 kernel 分数继续叠加。交付时明确哪些行为已测试、哪些只在 CPU 工具层检查、哪些仍需实际 Thor 验证。
